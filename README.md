# AIPMAssistant

AI-ассистент проектного менеджера — MVP по кейсу Xpage. Разбирает проектную коммуникацию,
собирает единый трекер задач и договорённостей и формирует post-meeting в формате Xpage.

Стек: .NET 8, Blazor Server, PostgreSQL 17 + pgvector, EF Core 8.
TargetFramework — `net8.0`; SDK 9 и 10 собирают его без изменений.

---

## Запуск

```bash
docker compose up -d                      # PostgreSQL с pgvector на localhost:5433
dotnet restore
dotnet build
dotnet run --project src/Pm.Web           # http://localhost:5080
```

Порт 5433, а не 5432: на 5432 обычно уже слушает локально установленный PostgreSQL,
и приложение молча уходит к нему вместо контейнера.

### Если при старте `28P01: password authentication failed`

Приложение достучалось до какого-то PostgreSQL, но не до нашего. Две причины:

1. **Отвечает чужой сервер.** Проверьте, что на порту именно контейнер:

   ```bash
   docker compose ps
   docker exec -it aipm-postgres psql -U aipm -d aipm -c "select version()"
   ```

2. **Том остался от прошлого запуска.** `POSTGRES_PASSWORD` применяется только при первом
   создании тома, поэтому смена пароля в compose ничего не меняет. Пересоздать:

   ```bash
   docker compose down -v
   docker compose up -d
   ```

   `-v` удаляет том с данными — на MVP это безопасно, состояние восстанавливается кнопкой
   «Загрузить материалы».

Схема БД создаётся на старте (`EnsureCreated`), миграций пока нет — на четырёхдневном MVP
модель меняется по нескольку раз в день. Перед пилотом на реальных данных перейти на миграции:
`dotnet ef migrations add Initial --project src/Pm.Infrastructure --startup-project src/Pm.Web`.

Дальше в интерфейсе: **Загрузить материалы** → **Прогнать все источники** → открыть трекер проекта.

### Ввод и выгрузка

Материалы больше не обязаны лежать в репозитории:

- **в интерфейсе** — «Загрузить файл материалов» на странице «Источники» принимает один JSON
  того же вида, что файлы в `materials/`;
- **в консоли** — `ingest` принимает файл или папку (см. ниже);
- **корень** с `materials/`, `golden/` и `reports/` задаётся переменной `PM_ROOT`. Без неё путь
  ищется вверх по дереву до `AIPMAssistant.sln` — то есть из checkout всё работает как раньше,
  а опубликованное приложение больше не падает на старте.

Выгрузка — обычные GET-ссылки, их же берёт сторонний сервис:

```
/export/{projectId}/tracker.json
/export/{projectId}/tracker.md
/export/postmeeting/{sourceId}
```

### Консоль

```bash
dotnet run --project src/Pm.Cli -- ingest ./inbox/urbankey-call.json
dotnet run --project src/Pm.Cli -- run urbankey          # или --all
dotnet run --project src/Pm.Cli -- export urbankey --out ./out
dotnet run --project src/Pm.Cli -- postmeeting urbankey.call --out ./out
dotnet run --project src/Pm.Cli -- llm-log --last 20
```

Код возврата 0 — успех, 1 — ошибка; конфигурация читается из `src/Pm.Web/appsettings.json`
(необязательно) и переменных окружения (`Llm__Provider`, `ConnectionStrings__Postgres`).

### Прогон метрик

```bash
dotnet run --project src/Pm.Eval -- --set dev        # UrbanKey + RetailFlow
dotnet run --project src/Pm.Eval -- --set holdout    # IndustryPulse + стресс-тест
dotnet test                                          # юнит-тесты
```

Отчёт пишется в `reports/eval-<набор>-<дата>.md` вместе с дельтой к предыдущему прогону.
Код возврата 2 — провалена бинарная метрика (выдуманные сроки, дубли на стресс-тесте, утечки);
прогон можно ставить в CI.

## Что здесь есть

```
src/Pm.Domain          сущности и перечисления, без зависимостей
src/Pm.Application     пайплайн, резолвер, парсер сроков, post-meeting, срезы трекера, выгрузка
src/Pm.Infrastructure  EF Core, pgvector, провайдеры LLM и эмбеддингов, загрузчик материалов
src/Pm.Web             Blazor Server: проекты, источники, трекер, экран созвона, выгрузка
src/Pm.Cli             консольный интерфейс к тому же пайплайну
src/Pm.Eval            прогонщик метрик
tests/Pm.Tests         xUnit: резолвер, разбор ответа модели, загрузчик материалов,
                       парсер сроков, валидатор цитат, PhrasingGuard, срезы трекера
materials/             13 файлов: три проекта по четырём источникам + стресс-тест
golden/                эталон на 29 сущностей, три эталонных post-meeting, инструкция по разметке
```

Прогон источника идёт в одной транзакции: падение на середине откатывает всё, источник
остаётся непомеченным, повторный прогон чистый. Журнал LLM пишется отдельным подключением
и откат переживает — иначе запись о провалившемся вызове исчезала бы вместе с ним.

### Пайплайн

```
Загрузка → тредирование → извлечение (LLM) → валидация цитат → парсер сроков → резолвинг → трекер
```

Три решения, на которых всё держится.

**1. Модель не возвращает дату.** Она возвращает цитату — `«завтра до 15:00»`. Дату считает
`DeadlineParser` от даты источника. `QuoteValidator` проверяет, что цитата дословно есть в тексте
сообщения, и обнуляет поле, если нет. Запрет «сервис не придумывает дедлайн» выполняется
по построению, а не по формулировке промпта.

**2. Между извлечением и трекером стоит резолвер.** Он решает `New / Update / Supersede / Close / Noise`,
иначе стресс-тест даёт десять дублей, а RetailFlow — два взаимоисключающих требования по доставке.
Guard от переслияния (порог 0.45) при сомнении заводит новую сущность: потерянная договорённость
хуже дубля.

**3. Post-meeting раскладывается кодом.** Модель может только переписать формулировку пункта;
`PhrasingGuard` проверяет, что число пунктов не изменилось и в тексте не появилось дат, чисел
и имён, которых не было во входных данных. Не прошло — берётся неотполированный вариант.

## Конфигурация

`src/Pm.Web/appsettings.json`.

### LLM

| `Llm:Provider` | Что делает |
|---|---|
| `Heuristic` (по умолчанию) | Офлайн-baseline на правилах. Работает сразу после clone, без модели |
| `OpenAiCompatible` | Любой эндпоинт `/v1/chat/completions`: облачный или локальный vLLM/Ollama |
| `Anthropic` | Claude через официальный SDK |

Переключение на локальную модель в контуре Xpage — три строки конфига, кода это не касается:

```json
"Llm": {
  "Provider": "OpenAiCompatible",
  "BaseUrl": "http://localhost:11434/v1",
  "Model": "qwen2.5:32b-instruct"
}
```

Ответ запрашивается через `response_format: json_schema` со `strict: true`; если провайдер
схему не поддерживает, клиент повторяет запрос в режиме `json_object`. В каждом режиме до трёх
попыток с паузами 1/2/4 с — повторяются только сетевые сбои, таймауты, 429 и 5xx.

#### Claude

```json
"Llm": { "Provider": "Anthropic", "Model": "claude-opus-5" }
```

Ключ — переменной окружения `ANTHROPIC_API_KEY` (SDK читает её сам) либо `Llm__ApiKey`;
в `appsettings.json` его класть не нужно. У Anthropic нет эндпоинта `/v1/chat/completions`,
поэтому это отдельный клиент, а не `BaseUrl` у `OpenAiCompatible`.

Три отличия от остальных провайдеров, заложенные в коде:

- `Llm:Temperature` не отправляется — на этом семействе моделей параметр удалён и даёт 400;
- строгий JSON идёт через `output_config.format`, режим `json_object` не нужен, и схемы
  из `Prompts` подходят как есть — они уже с `additionalProperties: false` и полным `required`;
- ретраи делает сам SDK, поэтому своего цикла попыток здесь нет.

Отказ модели приходит как HTTP 200 со `stop_reason: refusal` — клиент проверяет это явно
и бросает исключение, иначе источник молча получил бы ноль кандидатов. Серверные
fallback-модели на случай отказа не включены; для разбора проектной переписки это
избыточно, но при необходимости добавляется параметром запроса.

Только этот провайдер заполняет в журнале настоящие токены (`InputTokens`/`OutputTokens`) —
у остальных там символы, по которым стоимость не оценить.

### Журнал обращений к модели

Одна запись на попытку HTTP, а не на логический вызов: иначе отказ строгой схемы прячется
за успешным повтором. Пишется и провайдером `Heuristic`, переживает `Reset`, читается
через `dotnet run --project src/Pm.Cli -- llm-log`.

`Llm:LogPayloads` (по умолчанию `true`) добавляет в запись сырой запрос и ответ модели.
Проект демонстрационный, материалы синтетические; перед реальной перепиской — выключить.

### Эмбеддинги

`Embeddings:Dimensions` **обязано совпадать** с типом колонки `vector(N)`. Меняете модель —
меняйте размерность и пересоздавайте базу (`dotnet run --project src/Pm.Eval -- --recreate`).

| `Embeddings:Provider` | |
|---|---|
| `CharNGram` (по умолчанию) | Хешированные символьные триграммы, 256 измерений, офлайн |
| `Http` | `/v1/embeddings` — bge-m3, e5; поставьте `Dimensions: 1024` |

## Про baseline и честность метрик

Провайдер `Heuristic` — не заглушка и не имитация работы: он реализует тот же интерфейс,
что и модель, и через него проходит весь пайплайн. Его цифры — **нижняя граница**, с которой
сравнивается LLM-конфигурация.

Что baseline на текущих материалах делает хорошо: все шесть относительных сроков UrbanKey
разбираются верно (`«завтра до 15:00»` → 09.09 15:00, `«до среды»` → 09.09, `«11 сентября»` → 11.09),
выдуманных сроков — ноль.

Где он предсказуемо не дотягивает: **стресс-тест даёт 2 новые сущности вместо 0**. Причина
не в порогах резолвера, а в том, что эвристика не умеет формулировать заголовок по смыслу
и берёт сырой текст реплики. Реплика PM «Тогда фиксирую как открытый вопрос» и сообщение
стресс-теста «Канал уведомлений пока не выбрали» описывают одно и то же, но по словам
не пересекаются — близость 0.40 при пороге слияния 0.58.

Это чинится не подкруткой порога, а осмысленным заголовком от модели: она в обоих случаях
напишет «Канал уведомлений не выбран». Порог намеренно не подгонялся под эти два случая —
подгонка под тест на защите видна сразу.

## Наборы dev и holdout

| Набор | Проекты | Использование |
|---|---|---|
| `dev` | UrbanKey, RetailFlow | Настройка промптов и порогов |
| `holdout` | IndustryPulse, стресс-тест | Только замер |

Эталонного набора ожидаемых задач заказчик не прислал, поэтому `golden/` размечен нами.
Правила разметки — в `golden/annotation-guide.md`; крутить промпты на всех проектах и на них же
показывать метрики означало бы подгонку под тест.

## Что сознательно не сделано

Функциональные ограничения кейса, а не нехватка времени:

- сервис не общается с клиентом — кнопка называется «Скачать черновик», а не «Отправить»;
- не назначает исполнителей внутри команды и не меняет сроки;
- не создаёт задачи в Bitrix;
- нет интеграций с Telegram, MAX и почтой — коммуникация подаётся готовым JSON
  (файлом через интерфейс, путём через CLI), забирать её из мессенджеров сервис не умеет;
- нет распознавания аудио: транскрипты в материалах уже текстовые.
